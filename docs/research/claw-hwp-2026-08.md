## 잘 만든 곳 (우리가 배울 것)

1. **HWP5 CFB in-place 섹터 패치** (`patchInPlaceSectors`, cell-patch.js:1231-1346): CFB FAT/miniFAT
   직접 파싱→Section 체인만 패치→같은 섹터에 write-back, 체인 확장·mini→regular 승격까지. 동기:
   **rhwp `exportHwp()` 산출물은 한컴독스가 거부**한다(코드 주석 실측). `.hwp`를 `.hwp`로 돌려주는 유일한 길.
2. **`references/hwp-internals.md` = .hwp 쓰기 함정 등록부**: `nchars` 최상위비트 0x80000000(마지막 문단
   마커 — 중간에 세우면 한컴이 20억자로 읽음), 빈 셀은 PARA_TEXT 없는 네이티브 빈 문단으로, BinData
   삭제 시 스트림 재번호(rename) 필수, BorderFill 1-based, PrvImage 무효화(redaction 누수 차단).
   스펙에 없는 라운드트립 실측 지식.
3. **`fit` 길이 보존 채우기** (fitValueIntoLayout, 12줄): 셀 원문의 가장 긴 공백런에 값을 끼우고 같은 수의
   공백을 지워 총 길이 불변 → `"성명    (인)"` 위치정렬이 안 밀림. 조판 없이 서식을 지키는 우회 —
   우리 벌크 채우기(073)에 없는 아이디어.
4. **secure-fill 정책**: PII 값은 도구가 in-process로만 다루고 에이전트는 키 이름만 봄, 라벨 중복 매칭
   시 채우지 않고 거부, verify는 마스킹. 보안 주장 범위를 스스로 축소 명기("업로드 순간 이미 유입").
   우리 데모 AI·벌크의 개인정보 규약으로 이식할 만함.
5. **.hwpx deep 표 인덱스** (`tablesDeep`/`getTable`): 재귀 pre-order 수집으로 구조 op 27종 전부가
   중첩 표에 도달 — 우리 hwp-ops 구조 op CellPath 확장(후속)의 참고 형태.

## 약한 곳 (그대로 쓰면 안 되는 이유)

테스트 0(22.6K줄 바이트 수술에 회귀망 없음) · `.hwp` 편집이 **원본 파일을 백업 없이 덮어씀**(.hwpx는
`_edited` 사본 — 위험한 쪽이 기본값) · SKILL.md↔코드 드리프트(문서는 "중첩 셀 불가", 코드는 deep 인덱스로
가능) · 같은 문서에서 표 인덱스 체계 3벌 불일치 · rhwp의 `*ByPath` API 호출 0건(있는데 안 씀, 손으로
레벨 산술) · 중첩 표를 **발견할 수단이 없음**(.hwp inspect가 최상위만 열거).

## 중첩 표: 우리 캐럿 갭의 해법이 있는가 — **없다**

그들은 애초에 캐럿이 없다(에이전트가 셀 전체를 문자열로 바꾸는 모델). `.hwp` 트랙은 레코드 level 산술
(+2/깊이)로 `set_cell_text`/`collapse` 둘만 중첩 도달, 기하·발견 수단 없음. 우리는 기하·정체성·렌더·
경로 히트테스트·`SetTableCellPath`를 전부 갖췄고 막힌 건 캐럿 읽기 레인 하나(→ 이슈 081). **베낄 것 없음.**
